# 实测：浏览器内本地模型能否批改（结论：不能）

这次实测是为了回答一个具体问题：**能不能让网页自己批改、免 Key、且手机能用？**
路线是 WebLLM + WebGPU，在浏览器内跑一个小模型。

## 实测条件

| 项 | 值 |
|---|---|
| 模型 | Qwen2.5-1.5B-Instruct-q4f16_1（约 1GB） |
| 运行时 | WebLLM 0.2.86 / WebGPU / 真实 Chrome |
| 硬件 | RTX 5060 Laptop |
| 题目 | 四篇同题作文，真实给分 11 / 8 / 5 / 2 |

基准选这四篇，是因为它们是最锋利的测试：**连排序都做不到的模型，不配批改。**

## 结果

| 真实分 | 模型给分 | 模型给的四项分 |
|---|---|---|
| 11 | 11 | 4 / 3 / 2 / 2 |
| 8 | **12** | 4 / 3 / 2 / 2 |
| 5 | **10** | 4 / 3 / 2 / 2 |
| 2 | **12** | 4 / 3 / 2 / 2 |

**模型对四篇给出了完全相同的分项（4/3/2/2）**，只把总分做了抖动。那篇 2 分的作文
（语法近乎瓦解）被判成 **12/15**，与 11 分的作文几乎同分。**排序错误。**

这不是标尺的问题——模型根本没有在区分文本，它输出的是一个固定模板。
1.5B 低于这类任务的能力下限。

## 附带实测出的工程数据

| 项 | 实测 |
|---|---|
| 模型加载 | **221 秒 / 约 1GB**（桌面 + 光纤） |
| 单篇推理 | 约 2.1 秒（这部分不是瓶颈） |
| 权重可用源 | 魔搭 modelscope.cn（支持 Range 206） |
| WASM 模型库可用源 | fastly.jsdelivr.net/gh |
| **不可用源** | huggingface.co、raw.githubusercontent.com、cdn.jsdelivr.net 全部 000；**hf-mirror 虽然 curl 能看到 CORS 头，浏览器仍拒绝** |

## 对"手机能用"意味着什么

即便不考虑质量，手机上还有三道过不去的坎：

1. **微信内置浏览器**：查不到 WebGPU 支持证据，安卓微信走 XWeb 内核、Chromium 版本落后
2. **iOS**：Safari 26 / iOS 26 才完整支持，旧版没有
3. **安卓**：需 Android 12+ 且 GPU 兼容；外加首次约 1GB 下载、推理占 1.5–2GB 内存

而质量这一关（上表）在桌面、在有独显的机器上就已经没过。

## 结论

**浏览器内小模型批改这条路不可行**，原因不只是工程摩擦，而是模型能力不足：
1.5B 在这个任务上退化成输出常量。

一个前沿大模型 + 同样的标尺，实测精确档位一致率也只有 44%；指望 1.5B 做同一件事
不现实。要提升只能上更大的模型，而更大的模型在手机上更不可能跑。

**四条要求（免 Key / 网页自己算 / 手机能用 / 评分可信）无法同时满足。**
本项目的既有两条路径（复制模式、自动模式）已经覆盖了前三条中的不同组合：
复制模式满足免 Key + 手机能用 + 可信，自动模式满足网页自己算 + 手机能用 + 可信。

# 附：纯规则引擎评分实测（同样不可行）

为回应"用规则引擎在手机浏览器上直接评分"的方案，把该方案**逐字实现**
（14 条正则规则、同一套停用词与扣分逻辑、同样的四舍五入），拿真实标分作文实测。

## 结果

| 真实分 | 算法总分 | 内容/结构/词汇/语法 |
|---|---|---|
| 11 | **12** | 5 / 1.2 / 2.6 / 3 |
| 8 | **11.5** | 5 / 1.2 / 2.1 / 3 |
| 5 | **12.5** | 5 / 2 / 2.6 / 3 |
| 2 | **11** | 4.5 / 1.2 / 2.5 / 2.6 |

- **排序错误**：5 分那篇（12.5）比 8 分和 11 分的都高
- **分数跨度只有 1.5 分**，真实跨度是 9 分
- **语法项几乎全是满分 3/3**：14 条规则一条都没命中。那篇 2 分作文里满篇的
  `they are has parents`、`They are takes much love`、`childrens` 都不在规则表里

## 为什么这不是"规则写少了"

把规则表从 14 条扩到 200 条看似能解决，但本仓库早先的独立测量已经否掉了这个方向：
用 16 类错误模式的更宽探针集（含不可数复数、双谓语、there have、although...but 等）
统计语料，**4 分作文的探针命中数低于 12 分作文**——表面模式不预测档位。

原因是结构性的：**老师的给分跟着"句子读不读得通"走，而"读不通"需要解析句子，
不是模式匹配。** 正则抓得到零散特征，抓不到"整句话的结构塌了"。

## 样本边界

本次仅 4 篇（能拿到明确标分的文字源就这些）。它是个锋利但样本很小的测试：
**它证明了这套实现在这 4 篇上排序失败，不等于任意规则引擎都不可能。**
但方向上与此前的独立测量一致。

## 因此采用的方案：预检只产事实，不产分数

规则引擎当评分器不合格，但**当客观核查器完全合格**。`assets/js/precheck.js` 因此只输出
确定性事实：

- 字数与**官方扣分表**（逐段查表，含四级 ≤49 词扣 9、六级 ≤79 词扣 9 的陡增段）
- 段数与结论段标记
- 句长分布、句式类别（近似统计）
- 套话命中清单、高频重复词

这些事实会写进批改指令，让批改模型"有据可依"；**档位判断始终由模型完成**。
页面与指令中都显式声明"这些是事实而非评分"。

这样手机端拿到的是一条**手机可用、免 Key、且不撒谎**的路径：
预检瞬时完成、零流量，但它从不假装自己给出了成绩。
